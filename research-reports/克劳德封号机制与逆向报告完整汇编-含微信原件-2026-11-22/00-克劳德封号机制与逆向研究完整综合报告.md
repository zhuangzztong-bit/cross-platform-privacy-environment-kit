## 一、核心结论摘要

1. **封号不是“前端中文特征打分器”，而是五层复合风控体系**：Anthropic 的真实风控链路贯穿 **网络与 IP/ASN 层 → 客户端遥测与指纹层（Sift / Datadog / Sentry / GrowthBook）→ 请求协议与客户端真伪校验层（OAuth / `cch` 签名 / Beta 与工具形状）→ 支付与 Persona 3D 活体 KYC 层 → 服务端反滥用/反蒸馏分类器**。
2. **处罚分两条独立轨道**【官方/多源证据】：
   - **Token / 请求级拒收**：把 Pro/Max 订阅 OAuth Token 挪用于非官方客户端（包括第三方套壳、甚至自家 Agent SDK）时，服务端直接拒收请求（429/鉴权失败），但账号本身未必立刻封禁，换回官方客户端可能恢复。
   - **账号级永久封禁**：由反滥用/反欺诈分类器自动触发，余额通常不退；官方 Transparency Hub 2025 下半年数据显示，累计封禁约 **145 万账号**、收到约 **5.2 万次申诉**、仅约 **1,700 例翻盘（≈ 3.3%）**。
3. **跨端泄露强度差异巨大**【源码/抓包实证】：
   - **Android 端采集最重**：是三端中唯一把不可重置的系统级 `ANDROID_ID`（SSAID）原值交给第三方反欺诈服务 Sift 的客户端，且在登录前即采集、枚举全网卡（含开 VPN 仍暴露的公网 IPv6）与 SIM 卡 MCC/MNC。
   - **Desktop 与 CLI 不读主板/硬盘硬件序列号**：证伪了坊间“PC 端永久硬件封禁”的传言，但二者都会在**未登录或使用第三方中转**时把 `ant-did`、Sentry 时区/语言、以及第三方中转域名（`inference_host` / `apiBaseUrlHost`）明文上报给 Anthropic。
   - **Web 端依赖 Sift 1x1 GIF 隐蔽信标 + Datadog RUM + hCaptcha 证明链**；进入复核阶段后，**Persona KYC 会通过 WebRTC STUN（UDP）直接探测真实出口与内网 IP**。

### 3.2 Web 端：Sift 1x1 GIF 隐蔽信标与证明链【源码/抓包实证】

根据 `ImNotDragon` 的 CDP 实测与脚本解包：

- **脚本载体**：`https://s-cdn.anthropic.com/s.js`（约 57.9 KB Gzip），内嵌定制版 Sift Science、Crypto-js、`fingerprintjs2`、FingerprintJS v3 与 `detectIncognito`。
- **上报方式**：不走常规 JSON POST，而是将完整环境与指纹序列化进 `GET https://s-cdn.anthropic.com/images/476833.gif?...` 查询串：

| Query 参数 | 典型中国环境值 | 含义与来源 API |
|---|---|---|
| `to` | `-480` | `Date.prototype.getTimezoneOffset()`（UTC+8 为 `-480`） |
| `d` | `0` | 夏令时偏置（DST，美西夏令时为 `60`） |
| `ft` | `Asia/Shanghai` | `Intl.DateTimeFormat().resolvedOptions().timeZone` |
| `l` | `zh-CN` | `navigator.language` |
| `cf` / `fvch` / `fad` / `fmf` | 哈希值 | Canvas 2D / WebGL GPU / AudioContext / 系统字体度量指纹 |
| `inc` / `wd` | `false` / `false` | 隐身模式（`detectIncognito`）/ 自动化标识（`navigator.webdriver`） |
| `hc` / `fdm` / `tp` | 硬件数值 | CPU 核心数、内存 GB 等级、最大触摸点数 |

- **实时 RUM 与人机证明**：`claude.ai/api/v2/rum` 每 30 秒上报 `device.locale` 与 `device.time_zone`；注册与高敏操作通过 hCaptcha HSW Proof-of-Work 签发 `client_attestation`（`P1_*`）。

### 3.3 Android 端：全链路硬件与网络探针【源码/抓包实证】

`B1anYu/android.md` 与 `ImNotDragon` 交叉证实 Android 客户端是防线最重的一端：

- **自实现 Sift 协议（非外部 SDK）**：版本硬编码 `"1.3.1"`，向 `v3/accounts/{account}/mobile_events` 上报；挂载在 `Application.ActivityLifecycleCallbacks.onActivityCreated`，**每个界面创建（含未登录启动）即触发采集**。
- **核心泄露点**：
  1. `Settings.Secure.getString("android_id")` 原值上报（不加盐不哈希，卸载重装不重置）。
  2. 枚举 `NetworkInterface.getNetworkInterfaces()` 并仅剔除回环地址，导致**物理蜂窝/Wi-Fi 网卡分配的公网 IPv6 在开启 VPN 时照样上报**，可反查真实运营商与省份。
  3. `TelephonyManager` 读取 `getSimCountryIso()`、`getNetworkCountryIso()`、`getSimOperator()`（如 `46000`/`46011`）及运营商明文名称，与代理出口地形成直接冲突。
  4. Root / Hook 检测清单（`/sbin/su`、`/system/xbin/su` 等路径与 `de.robv.android.xposed.installer` 等 17 个包名）+ `ro.debuggable` / `ro.secure`。
  5. `AndroidKeyStore`（TEE / StrongBox）生成硬件非对称密钥对用于 `verify_magic_link` / `trusted_devices` 挑战签名 + Google Play Integrity 认证。

### 3.4 Desktop 与 CLI：未登录发包、明文中转与跨端关联边界【源码/抓包实证】

这部分直接补齐了此前两份 Windows MSIX 静态逆向笔记中“未追深层遥测载荷”的空白：

- **Desktop 未登录（哪怕仅用 BYOK 第三方 Key）冷启动仍发出 3 条带 `ant-did` 的出站请求**：
  1. `POST https://claude.ai/api/event_logging/v2/batch`：携带 `install_id`（`ant-did`）、机型画像（`os_build`/`cpu_model`/`total_memory`），以及明文 `inference_provider` / `inference_host` / `inference_base_url`。
  2. `GET https://api.anthropic.com/api/desktop/.../update?device_id=<ant-did>`：URL 明文携带安装 ID。
  3. Sentry（`*.ingest.us.sentry.io`）：携带 `user.id = ant-did` 与 `contexts.culture{locale, timezone}`（如 `zh-CN`、`Asia/Shanghai`）。
- **Desktop 硬件锚定（DeviceRegistry）**：不是读取主板序列号，而是调用 `@ant/claude-native` 的 `hardwareKeyGetOrCreate` 在 macOS Secure Enclave / Windows TPM / Linux（`5.1231.0+`）TPM 2.0 中生成随机 P-256 密钥对，将公钥注册到组织远程设备表并用于会话签名。
- **CLI 第一方判定陷阱**：决定是否开启遥测的函数只检查 `CLAUDE_CODE_USE_BEDROCK`/`VERTEX`/`FOUNDRY` 与网关凭据，**完全不看 `ANTHROPIC_BASE_URL`**。因此仅配置自建中转站时：
  - 一方事件流（`tengu_*`）与 GrowthBook 实验配置照常直连 `api.anthropic.com`；
  - GrowthBook 会把 `new URL(ANTHROPIC_BASE_URL).host` 作为 **`apiBaseUrlHost` 明文上传**；
  - 每次 `/v1/messages` 请求体强制注入 `metadata.user_id`（JSON 含 `device_id`、`account_uuid`、`session_id`，上限 512 字节），**不属于遥测通道，任何遥测环境变量均无法关闭**。
- **Desktop 与 CLI 是否关联成同一台机器**：
  - **强关联（必然成立）**：在 Desktop 内部拉起 Claude Code / Cowork 会话时，同一条 `desktop_ccd_*` 事件同时写入 `install_id`、`account_uuid` 与 `cli_session_id`，且注入同一 OAuth Token。
  - **独立终端运行 CLI 时**：代码层不存在直接互通桥，且传输栈不同（Desktop 走 Chromium/Electron，CLI 走 axios/Bun fetch）；唯一机械关联是**同一出口 IP + 时间窗**，或两端同时存在同名插件/技能时服务端对滚动哈希的重算比对。

## 四、克劳德封号机制的四大核心触发链路

### 4.1 链路一：环境与地理立体交叉校验（外围域名分裂是高频雷区）

当账号触发环境风控时，常见封号文案为：

> `An internal investigation of suspicious signals associated with your account indicates a violation of our Usage Policy.`

核心触发条件在于**多维信号不一致**，尤其容易在**外围域名出口分裂**时暴露。依据 `B1anYu`、`ImNotDragon` 与 `one-exit` 汇总，与 Claude 账号风控强关联的域名生态涵盖五大类：

### 4.2 链路二：反套利与客户端真伪校验（订阅 OAuth 封堵与 `cch` 签名）

2026 年 1 月起，Anthropic 将“消费级 Pro/Max 订阅 OAuth Token 挪用于非官方客户端（包括 OpenCode、Cline、各类中转桥，甚至 Anthropic 自家 Agent SDK）”及“账号拼车/转售/自动化批处理”列为头号治理目标。服务端校验已演进到协议载荷深层【源码/抓包实证】：

1. **System Prompt 首块归因头**：官方 Claude Code 每次请求会在 `system[0]` 写入：
   ```text
   x-anthropic-billing-header: cc_version=<version>.<3-char-fp>; cc_entrypoint=<entrypoint>; cch=<5-hex>;
   ```
   紧随官方身份声明块 `You are Claude Code, Anthropic's official CLI for Claude.`。
2. **`cch` 请求完整性哈希（`BYK/loreai` 逆向证实）**：
   - 将序列化后的请求体（含占位符 `cch=00000;`）输入 **Bun / Zig 标准库变体的 xxHash64**，取低 20 位转 5 位小写十六进制。
   - 关键工程特征：该实现使用了非标准常数 `PRIME64_4 = 0x85ebca77c2b2ae63`（标准 xxHash64 为 `0x85ebca6b3b7b36ef`），近期版本种子为 `0x4d659218e32a3268`。
3. **版本漂移指纹与工具形状门控**：
   - `anthropic-beta` 集合随版本精确增减并按模型代际门控（如 `claude-code-20250219`、`oauth-2025-04-20`、`mid-conversation-system-2026-04-07` 等）。
   - 工具命名受服务端校验（如黑名单 `todowrite`、拒收 `mcp_` 前缀、偏好官方 PascalCase 工具集）。
   - OAuth 令牌交换阶段在不同版本曾校验底层 HTTP 客户端指纹（如早期 `axios/1.13.6` 特征，v2.1.195 起迁移至原生 fetch）。

### 4.3 链路三：反蒸馏与中转溯源（3-bit 提示词隐写术实证）

在 2026 年 4 月 2 日（`v2.1.91`）至 2026 年 7 月 1 日（`v2.1.196`）期间，官方 Claude Code CLI 曾静默部署了一套穿透代理的**格式隐写机制**（Anthropic 事后承认其为反代充/反蒸馏实验，并于 `v2.1.197` 移除）【源码实证】：

- **触发条件**：仅当设置了非官方 `ANTHROPIC_BASE_URL` 时执行。
- **信号来源**：
  1. 系统时区是否命中 `Asia/Shanghai` 或 `Asia/Urumqi`（1 bit）。
  2. `ANTHROPIC_BASE_URL` 域名是否命中内置 **Base64 + XOR(key=91)** 解码后的 147+ 国内企业/中转域名表（如 `*.cn`、`baidu.com`、`alibaba-inc.com`、`bytedance.net`、`anyrouter.top` 等，1 bit）或 11 个国内 AI 实验室关键词（`deepseek`、`moonshot`、`minimax`、`zhipu`、`dashscope`、`volces` 等，1 bit）。
- **隐写编码表（嵌入系统提示词 `Today's date is YYYY-MM-DD`）**：

| 隐写维度 | 编码字符 / 格式 | 对应含义 |
|---|---|---|
| 日期分隔符（1 bit） | `2026-06-30` vs `2026/06/30` | 短横线 = 非中国时区；**斜杠 = 命中 `Asia/Shanghai` 或 `Asia/Urumqi`** |
| `Today's` 撇号（2 bit） | `'` (`U+0027`) | 均未命中 |
| `Today’s` 撇号（2 bit） | `’` (`U+2019`) | 命中 147+ 域名黑名单 |
| `Todayʼs` 撇号（2 bit） | `ʼ` (`U+02BC`) | 命中 AI 实验室关键词 |
| `Todayʹs` 撇号（2 bit） | `ʹ` (`U+02B9`) | 同时命中域名表与 AI 实验室关键词 |

此外，安全研究者还观察到部分封禁通知邮件内含 **1x1 追踪像素（tracking pixel）**，在非代理环境下加载邮件图片即可向服务端回传真实 IP 与设备信息。

### 4.4 链路四：支付风控、服务端行为分类器与 Persona 3D KYC

1. **支付与账单核验（高频“升级/续费瞬间秒封”）**【官方/多源证据】：代充（付款人与账号持有人不一致）、高风险虚拟/预付卡 BIN、发卡国/账单国/IP 属地冲突、拒付（chargeback）或 VoIP 接码号，均会触发 Stripe 与内部反欺诈拦截。
2. **行为与内容分类器（`automatic review of your recent activities`）**【官方/多源+服务端推断】：
   - 重度编码用量本身只触发**限流（throttle）**；但“多 IP 并发 + 异常吞吐 + 批量类蒸馏模式 + AUP 违规内容（恶意软件、未满 18 岁等）”会触发自动封禁，并通过支付卡、IP、设备标识波及关联账号。
   - 官方亦承认分类器存在误封（如 2026 年初收紧期间及部分扩展/后台子进程误触发案例），但普通用户申诉复核成功率极低（≈ 3.3%）。
3. **Persona 3D 活体 KYC 终审**【源码/抓包实证】：
   - 2026 年 7 月起，部分被标记账号需经 `portal.anthropic.com`（`PassportVerificationPortalService`）转入 Persona（`inquiry.withpersona.com`）提交政府证件与 3D 活体人脸。
   - 除 `tg.withpersona.com` / `fp-us-365.withpersona.com` 采集设备画像外，Persona 还会向 `webrtc-consumer.withpersona.com` 发起 **WebRTC STUN（UDP 报文）**——在仅配置常规 HTTP 代理的浏览器环境中，UDP 会直接绕过代理经物理网卡发出，向服务端暴露真实公网与局域网 IP。

## 五、源码逆向直接证伪的 5 个常见误区

1. **误区一：“PC 端会读取主板/硬盘序列号做永久硬件封禁”**  
   → **证伪**：Desktop 与 CLI 源码均不采集物理硬件序列号（桌面端 `ant-did`、CLI `userID`/`machineID` 均为随机值，Secure Enclave/TPM 也仅是随机生成的注册密钥对）。**真正上报不可重置系统硬码（`ANDROID_ID` 原值）和物理网卡 IPv6 的是 Android App。**
2. **误区二：“只把 `ANTHROPIC_BASE_URL` 指向自建中转，Anthropic 就完全看不到”**  
   → **证伪**：CLI 第一方判定不看 `ANTHROPIC_BASE_URL`，GrowthBook 仍定时直连官方并明文上报 `apiBaseUrlHost`；Desktop 未登录也会在一方事件里明文上报 `inference_host`。
3. **误区三：“配置 `DISABLE_TELEMETRY=1` 就彻底静默”**  
   → **证伪**：CLI 的遥测变量对 Desktop 完全无效；在 CLI 内，每次 `/v1/messages` 请求体强制携带的 `metadata.user_id` 属于推理载荷而非遥测通道，任何遥测开关都无法关掉。
4. **误区四：“同一台电脑同时装 Desktop 和 CLI 一定会本地互通连坐”**  
   → **修正**：独立终端跑 CLI 与未登录 Desktop 在代码层面没有直接桥接；真正产生硬关联的是**在 Desktop 内直接启动 Code/Cowork 会话**，或两端共用同一出口 IP 与时间窗。
5. **误区五：“`fuck-claude.vercel.app` 或同类检测页跑出低分就代表安全”**  
   → **证伪**：这类社区工具只覆盖浏览器表层启发式特征（且 `curl` 与浏览器实测结果截然不同），完全测不到 OAuth/`cch` 载荷校验、支付卡 BIN 与账单一致性、外围遥测域名出口分裂、Android `ANDROID_ID`/IPv6 泄露以及服务端行为分类器。
